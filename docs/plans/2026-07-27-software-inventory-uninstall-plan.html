Vitals · revised review plan · 27 July 2026

App visibility with a safe Homebrew path

A deliberately narrow plan: fix the destructive Homebrew cask false positive first, then expose protected application bundles with the smallest possible model/UI change. CLI package management is explicitly out of scope.

Revision 2 · implementation intentionally not started.

Ship order. PR 1 is the Homebrew ownership proof and its regression test, alone. PR 2 is the protected-application visibility change. Do not combine either with a package-manager or inventory-platform rewrite.

The current Applications surface remains the Applications surface. It does not become a general developer-package manager.

1. P0 safety bug — Homebrew cask false positive

Current flow: LeftoverScanner.homebrewCask(appName:installedCasks:) guesses a cask from the app display name, then AppUninstaller.homebrewUninstall runs brew uninstall --cask --zap. That is unsafe.

Data-loss risk

A manually downloaded Docker.app plus an unrelated installed docker cask can pass the name guess. Vitals then asks Homebrew to zap the cask and may remove the user’s Docker configuration/data even though Homebrew did not install the displayed app.

This is not an “ownership uncertain” metadata quality issue. A name match is not permission to invoke zap.

Minimal fix

  1. Keep homebrewCask only as a candidate-token lookup.
  2. Add caskOwns(appURL:token:) beside the existing Homebrew helpers.
  3. Validate the token against the existing lowercase-alphanumeric-hyphen grammar.
  4. Run the user’s absolute brew executable with brew list --cask <token>.
  5. Parse the reported artifact paths and require one canonical/standardized path to equal the displayed app bundle URL.
  6. Only if the path proof succeeds should prepareUninstall place the app in the cask map and allow the existing brew uninstall --cask --zap route.
  7. If proof fails, treat the app as an ordinary app: do not run Homebrew and do not zap.
let candidate = LeftoverScanner.homebrewCask(appName: app.name, installedCasks: casksList)
if let candidate, LeftoverScanner.caskOwns(appURL: app.id, token: candidate) {
    casks[app.id] = candidate
}

Use standardized URLs at minimum; resolve symlinks where the Homebrew output is a symlinked artifact. Do not use display-name equality as proof.

P0 regression test

  • Fixture app: /Applications/Docker.app.
  • Fixture candidate token: docker.
  • Mock brew list --cask docker output without /Applications/Docker.app.
  • Assert caskOwns is false and no cask uninstall plan is produced.
  • Add the positive case where the exact app path is listed and assert it is true.

Acceptance: a guessed token can never reach brew uninstall --cask --zap without an exact artifact-path match. This is the first ship and should be reviewed independently.

2. Small bug fix — protect every Vitals channel

AppInventory.isProtected currently protects the literal Vitals.app and the running bundle ID. That leaves Stable able to list Nightly or Dev as removable.

Extend the existing guard with the product bundle namespace:

if bundleID.hasPrefix("com.syntaxlabtechnology.vitals") { return true }

This requires no inventory rewrite. Add one test covering a different Vitals channel, for example com.syntaxlabtechnology.vitals.dev at /Applications/Vitals Dev.app.

3. Protected apps become visible

After the P0 safety patch, make the Applications list show all top-level application bundles in the defined application folders, including protected Apple/system apps and every Vitals channel. Protected rows show their real size but cannot be selected.

Discovery scope

  • Keep direct-child scanning. Do not recursively enumerate nested helper apps, .appex, XPC services, frameworks, or app internals as separate rows.
  • Keep the existing user roots: /Applications, /Applications/Utilities, and ~/Applications.
  • Add the direct system-visible roots needed for the “all applications” contract: /System/Applications and /System/Applications/Utilities.
  • Do not add Launch Services as a second discovery source. The direct filesystem scan remains authoritative for bundle rows and avoids stale registrations and duplicate identities.
  • Continue deduplicating canonical URLs and skip malformed entries only after recording a diagnostic; do not silently pretend an unreadable app does not exist.

Minimal model change

Add one field to InstalledApp:

let protectedReason: String?
  • nil means the row may be selected, subject to the existing fresh uninstall checks.
  • A non-nil reason means the row is visible, measured, locked, and excluded from selection.
  • Do not introduce a new kind/source/locations/removalPlan software platform for this change.
  • Keep AppInventory.isProtected as the safety predicate. Use it to populate the reason, and re-check it before building or executing an uninstall.

Minimal UI behavior

  • Keep the existing list, rows, search, sort, footer, confirmation sheet, and visual language.
  • Protected rows retain their icon/name/version/size and gain the existing lock affordance with a short reason such as “System app” or “Vitals”.
  • The row’s selection control is disabled when protectedReason != nil.
  • The headline count becomes the total visible application count. The footer selection count remains removable items only.
  • Do not add a package/CLI category, new navigation tab, or new developer-tool surface.

4. Removal rules retained

ItemBehavior
Plain removable .appExisting quit, leftover scan, Trash/admin flow, and final revalidation.
Homebrew cask with exact path proofExisting cask route; preview/confirmation remains required; zap is allowed only after proof.
Homebrew candidate without path proofNever invoke Homebrew. Handle only as a plain app if otherwise removable.
Apple/system/Vitals appVisible and sized, permanently unselectable.
System extensionDetect and explain that removal requires the vendor app/uninstaller or management workflow. Vitals does not deactivate another vendor’s extension.
Root-owned/admin-installed appUse the existing explicit admin path and fixed allowlists; never broaden path permissions because the row is visible.

Apple recommends an app-provided uninstaller when present because it may remove login items, extensions, and other data; otherwise Finder’s normal route is moving the app to Trash. Apple also says required macOS apps and apps in the System folder cannot be removed. Vitals should mirror that distinction in visibility versus selectability.

6. macOS 26/27 validation

  • Build and install only through apps/desktop/dev.sh; never disturb Stable.
  • On macOS 26, verify system app visibility, protected Vitals channels, exact cask ownership, false-positive Docker scenario, plain app uninstall, and Homebrew-owned app uninstall.
  • Repeat the same matrix on macOS 27 beta. The feature should rely on public Foundation/AppKit behavior and should not need a 27-specific deletion path.
  • Run the existing protection, leftover, script-safety, and uninstall tests plus the cask ownership regression fixture.

7. Ship checklist

  1. PR 1, alone: add caskOwns, gate the cask map on exact path proof, add positive/negative tests, verify no false-positive zap.
  2. PR 2: protect the entire Vitals bundle namespace, add the channel regression test, add protected rows with protectedReason, and add direct system application roots.
  3. Run Dev builds and the macOS 26/27 test matrix.
  4. Review every selected item’s plan before executing it; no guessed cask token may reach the destructive path.
