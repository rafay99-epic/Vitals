Clipboard and Drop: Mac, Android, iOS and web

Goal: see the Mac's clipboard history on the phone, and move text, links, images, files and folders in either direction without LocalSend. Android, iOS and the web client. Works over Wi-Fi and over Tailscale with the connection we already have. v2 of this plan (2026-10-24): auto-copy, pins, folders, the iOS share extension and the web client are all in v1. Clickable demo: Clipboard prototype. Branch feat/clipboard from nightly @ 16187b8.

Key findings

1. The transport is already solved. Add RPCs, get both routes free.

Wi-Fi: phone opens a Noise-encrypted WebSocket to Lan.ts, which proxies decrypted text frames to the gateway's loopback /ws. Tailscale: Serve terminates HTTPS and forwards to the same /ws. Both end in one Effect RPC server (VitalsRpc). Any new RPC works on both routes with zero transport code.

Three limits shape the design:

  • MAX_FRAME_BYTES = 1 MB per WebSocket frame (gateway and LAN listener).
  • RPC serialization is JSON (RpcSerialization.layerJson), and the LAN proxy only forwards string frames. So binary data travels as base64 in chunks. 512 KB raw per chunk is about 683 KB encoded, safely under 1 MB.
  • The Mac bridge (stdio NDJSON) caps lines at 1 MB. Blobs must not cross the bridge.

2. The Mac app and the gateway share a disk. Use it as the blob channel.

The gateway's data dir is RemoteModel.dataDirectory = ~/.vitals*/remote. The Swift app writes image/file bytes to remote/clips/ and sends only metadata over the bridge. The gateway streams those files to phones in chunks. Uploads from the phone land in the same folder, and the Mac app is told "put clip X on the clipboard". The bridge stays small, and it is channel-isolated for free.

3. macOS: poll changeCount, respect secret markers, watch the privacy API.

  • There is no pasteboard change notification. Clipboard managers poll NSPasteboard.general.changeCount (Maccy defaults to 0.5 s). Reading the counter is cheap; contents are read only when it changes.
  • macOS 15.4 added NSPasteboard.accessBehavior and a prompt for programmatic reads. Reports say it is still off by default on macOS 26 and only turns on through defaults. Plan for it anyway: check accessBehavior and show "Allow pasting in System Settings" instead of failing silently.
  • Password managers mark copies with org.nspasteboard.ConcealedType, TransientType and AutoGeneratedType. Never record those. Also skip copies made while an app on an ignore list is frontmost (1Password, Bitwarden, Passwords, Keychain Access).
  • Finder copies are file references, not bytes. Copy them into clips/ with an APFS clone (copyfile with COPYFILE_CLONE), which costs no disk space and is instant. Folders are out of scope for v1.

4. Android blocks background clipboard reads. Phone to Mac is Share sheet + one tap.

  • Since Android 10, an unfocused app reads an empty clipboard unless it holds READ_CLIPBOARD_IN_BACKGROUND, which only system apps get. So "auto-sync what I copy on the phone" is not possible in the background. It is possible when Vitals is open: a "Send what I copied" button reads the clipboard in the foreground.
  • The native way to send anything from the phone is the Share sheet. expo-sharing in SDK 58 can now receive shares (android.enabled, singleShareMimeTypes, multipleShareMimeTypes, useIncomingShare()), and it works with React Navigation's linking prop. It is marked experimental. One known bug: an ACTION_SEND with both text and an image loses one part (expo PR #51646, tagged for SDK 58).
  • Writing to the phone clipboard is fine in the foreground. expo-clipboard (already a dependency) does text and setImageAsync for images.

5. Live delivery only while the app is connected.

The phone has no push channel (alerts use a 15-minute background job). New Mac copies appear live while Vitals is open and connected, and the history list fills in on open. No fake "synced" state.

Architecture

Contracts (as built)

packages/contracts/src/clips.ts. One Clip for every direction, so a phone send shows up in history like a Mac copy.

Clip = { id, kind: "text" | "link" | "image" | "file" | "folder", at,
         deviceId (null = copied on the Mac), source (app or phone name),
         text, truncated, name, mime, bytes, files (folders), thumb (base64 JPEG), pinned }

ClipEvent = Snapshot { enabled, clips } | Added { clip } | Updated { clip } | Removed { ids }

CLIP_LIMITS = { chunkBytes: 512 KB, inlineText: 256 KB, previewText: 4 KB,
                thumbChars: 48 KB, itemBytes: 1 GB, batch: 50, snapshot: 200 }
RPCWhat it doesScope
clips.watchSnapshot, then live changes. Re-sends a Snapshot when history is turned on or off on the Macclipboard
clips.read{ id, offset } to 512 KB of base64 plus total and done. File and folder clips are cloned or zipped on the Mac on first readclipboard
clips.pin, clips.removePinned clips skip retention. Remove deletes the row and its fileclipboard
clips.send.begin / chunk / finishText and links finish in begin. Chunks are offset-aligned and written positionally, so up to 4 can be in flight in any order. Optional sha256 check at finishoperate
clips.put{ ids, to: clipboard | downloads, folder }. One call places up to 50 clips, so "2 photos" lands as one action and one Mac notificationoperate

Bridge, Mac app to gateway: clip (metadata only, plus stored file name or origin path), clipPolicy (enabled, keepDays), clipClear. Gateway to Mac: clipStats, and two queries, ClipMaterialize (clone a file or zip a folder into clips/) and ClipPut (place resolved items). Hello.clips tells a new phone the Mac supports all this; older Macs keep the old text-only sheet. ClipboardSet and clipboard.get stay for one release, then go.

Mac app (Swift)

  • Services/ClipWatcher.swift: UI-free. DispatchSourceTimer at 0.5 s with generous leeway so wakeups coalesce. It runs only when Remote is on and the new setting is on. Image encoding and thumbnailing (CGImageSourceCreateThumbnailAtIndex, 256 px JPEG) run off-main. TIFF screenshots are stored as PNG.
  • Reads in priority order: file URLs, image (.png, .tiff), URL, string. It skips the nspasteboard.org secret markers, the ignore list, empty strings, and strings over 10 MB.
  • Echo guard: after ClipPut writes, store the resulting changeCount and skip it, so a phone-sent clip doesn't come back as a duplicate "Mac" clip.
  • ClipPut in CommandRouter: resolves the file name strictly inside clips/ (no /, no .., test-locked like the uninstaller paths). For clipboard it writes NSImage, a file URL, or a string by kind. For downloads it copies to ~/Downloads with a unique name and reveals nothing.
  • Setting in Settings, Remote: "Clipboard history for phones", off by default. Shows "macOS is blocking clipboard reads" when accessBehavior says so. The existing per-device "Read clipboard" toggle in RemoteView keeps gating who sees it.
  • Perf: measure idle CPU with the watcher on vs off before merging (PR #151 rule). Expected cost is one integer read per tick.

Gateway (Bun + Effect)

  • src/clips/ClipStore.ts: migration adds a clips table (id, kind, at, origin, source_app, text, name, mime, bytes, sha256, thumb, file). It is the only owner of deletion.
  • Retention (defaults, open to change): newest 200 clips, 7 days, 1 GB of files, oldest first. Same sha256 as an existing clip bumps at instead of adding a row.
  • Uploads: clips/incoming/<uploadId>.part, offsets must be contiguous, size capped at 100 MB per item in v1, abandoned parts swept after 10 minutes, sha256 checked at finish.
  • Activity log: chunk RPCs log one summary line per transfer, not one frames row per chunk, so a 100 MB send doesn't write 200 rows.
  • scripts/fake-mac.ts: emits a few text, link and image clips, and answers ClipPut, so the phone can be built without a Mac.

Phone (React Native, Android and iOS)

  • Where it lives: Control. "Send to Mac" becomes "Clipboard": one line with the Mac's latest copy (Copy is one tap), then the same three tiles. The Clipboard tile pushes a Clipboard screen in a new Control stack. No new tab, nothing on Home.
  • Clipboard screen: compose field, Paste / Photos / Files tiles, a transfer card while sending, chips (All, Pinned, Text, Links, Images, Files), sections Pinned / Today / Earlier.
  • Clip sheet: one sheet, actions by kind. Copy, Open on this phone, Open on Mac, Save to Photos, Save to this phone, Save as zip, Share, Put on the Mac clipboard again, Pin, Remove (tap with Undo).
  • Send sheet: preview, "Put it on" Mac clipboard or Downloads, Send. The Photos tile, the Files tile and the share sheet all open it.
  • Transfers: shared engine in packages/app, 4 chunks in flight, resumes after a reconnect, Cancel, real byte progress in a card and a toast. Files stream through expo-file-system, never whole in JS memory.

Risks

RiskMitigation
Clipboard holds secretsOff by default, per-phone clipboard scope, secret markers and ignore list, 7-day retention, files stay in the channel's own data dir
macOS turns on paste promptsRead contents only when changeCount changes, detect accessBehavior, explain the fix in Settings
Big files over Tailscale relay are slowHonest byte progress, resumable chunks, 100 MB cap in v1. Measure real throughput in phase 4; quote no numbers before that
base64 + JSON overhead (about 33%)Accepted for v1. Later: msgpack RPC serialization plus binary LAN frames, which touches the protocol for every RPC
expo-sharing receive is experimentalPin the SDK, test text, image, multi-image and PDF shares; the text-plus-image case is a known gap
Echo loops and duplicateschangeCount echo guard on the Mac, sha256 dedupe in the gateway

Not in v1

  • Background delivery to the phone. There is no push channel by design, so Mac copies arrive while the app is open.
  • Picking a whole folder on the phone (Android SAF only). Groups of files cover it.
  • Binary frames (msgpack) to drop the base64 overhead. That changes the protocol for every RPC, so it gets its own PR.
