Vitals Drop: any file, any size, both ways

Goal: replace LocalSend. APKs, videos, photos, documents, whole folders, from the phone to the Mac and from the Mac to the phone, over your Wi-Fi or Tailscale. Files are files: they land in Downloads (or Files on iPhone), not on the clipboard. Builds on Clipboard and Drop (PR #165). Plan written 2026-10-24. Nothing here is built yet.

Where today's build stops

LimitWhy
1 GB per fileA cap we set because bytes travel as base64 inside JSON RPC calls, 512 KB at a time
Slow on big filesAbout a third extra bytes on the wire for base64. On Wi-Fi, every byte is also encrypted in JavaScript on the phone (@noble/ciphers ChaCha20 inside the Noise tunnel) and handed to native code as a string. Fine for a screenshot, painful for a 4 GB video
The Mac can't sendMac to phone only works for things you copied. There is no "send this file to my phone"
Phone downloads sit in a cacheYou have to tap Save every time. Nothing lands in Downloads or the Files app on its own
Stops in the backgroundTransfers run in the app's JavaScript, so they pause when you switch apps
No APK installThe app can't hand an APK to Android's installer

The idea: control stays on RPC, bytes move over HTTPS, natively

Keep the existing connection for everything small: offers, accept, progress, history. Move the file bytes to plain HTTPS requests handled by native code on the phone, streamed straight to and from disk. That is how LocalSend works too: each device runs an HTTPS server with a self-signed certificate, and peers check its SHA-256 fingerprint.

Three ways to move the bytes

OptionGoodBad
A. Keep RPC chunks, switch to binary (msgpack)Smallest change. Drops base64Still JS encryption on Wi-Fi, still JS in the byte path, still foreground only. Changes the protocol for every RPC
B. Native HTTP from Expo (expo-file-system downloads and uploads)No new native code. Streams to diskCan't pin a self-signed certificate, so it only works over Tailscale's real ts.net certificate. Wi-Fi at home would still use the slow path
C. Go transfer engine in the existing gomobile module (recommended)One implementation for Android and iOS. Pins the Mac's certificate on Wi-Fi, trusts ts.net on Tailscale. Streams disk to disk, resumes with Range requests, hashes as it goes. The app already ships Go (packages/tailnet), so it adds no new toolchainMost work. Needs a native rebuild (no OTA). Bridges, foreground service and Files integration still need small Kotlin and Swift pieces

Protocol

RPC (small, over the existing connection)
  drop.offer   { to, files: [{ name, size, mime, path, sha256? }] }  -> { dropId, files: [{ fileId, url }], ticket }
  drop.accept  { dropId }            the receiving side says yes (auto-yes for your own paired devices, a setting)
  drop.watch   stream of DropEvent   Offered | Accepted | Progress | FileDone | Done | Failed | Cancelled
  drop.cancel  { dropId }

HTTPS (bytes)
  PUT  /api/drop/:dropId/:fileId     Content-Range: bytes a-b/total, 16 MB parts, written in place
  HEAD /api/drop/:dropId/:fileId     which ranges arrived, so a resumed upload skips them
  GET  /api/drop/:dropId/:fileId     Range supported, so a resumed download picks up where it stopped
  Authorization: Drop <ticket>       one drop, one device, expires in an hour, never in the URL
  • Wi-Fi: the gateway opens one more HTTPS port next to the Noise port, with a certificate made once with openssl and kept in the data dir. Its SHA-256 key fingerprint travels in MacRoutes, which the phone only accepts over the already-authenticated Noise or Tailscale channel. The Go engine refuses any other certificate. That gives TLS 1.3 at native speed instead of ChaCha20 in JavaScript.
  • Tailscale: the same endpoints are served under the existing tailscale serve HTTPS address, with its real certificate. When both devices are on the same Wi-Fi, Tailscale usually finds a direct path anyway.
  • Integrity: the sender hashes while reading and the receiver hashes while writing. A mismatch throws the file away and says so.
  • Space: the receiver checks free space before accepting: "Your Mac needs 4.2 GB free for this".
  • Folders: phone to Mac keeps relative paths and recreates the folder in ~/Downloads/Vitals. Mac to phone sends each file with its path, so there's no zipping and no double disk use; Android saves them under Downloads/Vitals/<folder>.

Mac to phone (the new direction)

  • Ways to send: right-click in Finder › Quick Actions › Send to Phone (a macOS Service declared in Info.plist; it works in our SwiftPM app, unlike a Share extension). Or drag files onto the Vitals menu bar icon or Dock icon, or use a Send Files button under Remote. With more than one paired phone, a small picker asks which.
  • When the phone is open: the transfer starts at once and shows in the menu bar panel: "Sending to Pixel 9 Pro · 1.2 of 4.0 GB".
  • When it isn't: there is no push service by design, so the Mac shows "Waiting for Pixel 9 Pro. Open Vitals on the phone." and starts the moment it connects. Android's background check (every 15 minutes) can also start a waiting drop.

Phone to Mac

  • The share sheet sends files through Drop: any type, any size, several at once. Text and links keep going to the Mac clipboard as they do now.
  • Files land in ~/Downloads/Vitals (a setting), quarantined so Gatekeeper checks apps and installers, with a notification that has Show in Finder.

How it fits the app (mocks first)

  • Control: the Clipboard section gains one tile: Clipboard · Files · Open link · Find Mac. Clipboard stays text, links and images. Files is the LocalSend replacement.
  • Files screen: Incoming (from the Mac, with progress, then Open, Install, Save to Photos), Send (Files, Photos, Videos, plus whole folders on Android), and Sent. Nothing new on Home.
  • Share sheet: files go to Drop and open a small Send sheet showing "4 files · 3.2 GB". Text and links still go to the Clipboard sheet.
  • Mac: one Files card under Remote: receive folder, auto-accept from your own phones, Send Files. Progress shows in the menu bar panel.
  • As before: an HTML mock grid first, you pick, then code.

Security

  • The Wi-Fi certificate is pinned, using a fingerprint delivered over the authenticated channel. Tailscale uses its own identity plus our session.
  • Tickets are per drop and per device, short-lived, and never in URLs or logs. Scopes: operate to send to the Mac; Mac-initiated drops go only to the device the Mac picked.
  • Received files on the Mac are quarantined. Names are sanitized to one path component, paths can't escape the receive folder, and nothing is ever overwritten.
  • Size has no hard cap, but the receiver checks free space, and a setting caps how much a single drop may use.
  • The privacy policy gets updated before this ships, plus the Play declaration for APK installs.

One system, not two

Drop reuses the clip store and the shared folder. A drop is a set of file clips with a target and a state. Clipboard history keeps its small RPC path for text, links and images under 8 MB. Anything bigger, and every file you send on purpose, goes through Drop. Once Drop ships, the 1 GB base64 path for big files is retired.

Decisions for you

  1. Byte transport: the Go engine (C, recommended) or the quicker Tailscale-only native HTTP (B)?
  2. APK install: Dev and Nightly first, with Stable after the Play declaration?
  3. Where it lives: a separate Files tile and screen (recommended), or inside the Clipboard screen?
  4. Auto-accept: should drops from your own paired devices start without asking (recommended), with a switch to ask first?
